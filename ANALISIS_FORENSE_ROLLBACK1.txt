CORRECCIÓN TRAS ANÁLISIS DETALLADO:

Las rutas conflictivas NUNCA se eliminan de establishedRoutes durante
el rollback simple. El flujo correcto es:

Flujo del ROLLBACK SIMPLE (líneas 171-183 DFbFR*, 614-654 DFfullRuteoMin):
1. createBackups() → Crea copias de rutas en conflicto
2. Utils.deallocateFs() → Libera slots (setFree(true))
3. ❌ NO SE ELIMINAN de establishedRoutes (las rutas siguen en la lista)
4. Intenta asignar nueva demanda → FALLA
5. ROLLBACK: restoreSingleRoute() → Restaura slots (setFree(false))
6. Las rutas SIGUEN en establishedRoutes

ENTONCES: ¿Por qué conflictosEnLinkCoreVentana() retorna 0 rutas?

RESPUESTA: BUG DE DIRECCIONES INVERSAS

Las rutas que ocupan los slots en 2→6 están en establishedRoutes,
pero usan el enlace 6→2 en su path:

1. Utils.createTopology() crea 2→6 y 6→2 con MISMO List<Core> (líneas 68-81)
2. Una ruta con 6→2 llama assignFs() → marca slots en cores compartidos
3. 2→6 ve esos slots como ocupados (isFree=false)
4. conflictosEnLinkCoreVentana() busca rutas en 2→6 exactamente
5. posicionDelEnlaceEnRuta() compara direcciones exactas (línea 1023)
6. La ruta con 6→2 NO se detecta → retorna -1
7. Resultado: 0 conflictos detectados pero slots ocupados

Código relevante (línea 1023):
```java
private static int posicionDelEnlaceEnRuta(EstablishedRoute route, Link link) {
    int from = link.getFrom();
    int to = link.getTo();
    for (int i = 0; i < path.size(); i++) {
        Link li = path.get(i);
        if (li.getFrom() == from && li.getTo() == to) {  // ← DIRECCIÓN EXACTA
            return i;
        }
    }
    return -1;  // ← Ruta con 6→2 NO se detecta al buscar 2→6
}
```

   - conflictosEnLinkCoreVentana() retorna 0 rutas (INCORRECTO - no ve inversa)

CONCLUSIONES
=============================================================================

1. NO SE ENCONTRÓ evidencia directa en traces disponibles de una ruta 
   específica con 6→2, core 0, FS [0-2] (limitación de instrumentación).

2. Sin embargo, el MECANISMO está COMPLETAMENTE EXPLICADO:
   - 2→6 y 6→2 comparten List<Core> objects (comprobado en código)
   - posicionDelEnlaceEnRuta() solo detecta direcciones exactas (comprobado)
   - Esto causa que rutas con 6→2 ocupen slots que 2→6 ve sin detectarlas

3. El bug de direcciones inversas (A) ES la causa de ROLLBACK-1:
   - Explica por qué isFree=false (slots físicamente ocupados)
   - Explica por qué conflictSet pequeño (no detecta inversas)
   - Explica la contradicción slots ocupados / pocos conflictos

4. La ausencia de ruta concreta en traces se debe a:
   - Los traces NO capturan asignaciones RSA normales ("ASSIGNED")
   - Solo capturan logs de defragmentación (backups)
   - Las rutas con 6→2 existen pero con FS altos en logs disponibles

5. Los tres algoritmos de defragmentación comparten:
   - evaluarVentana() / evaluarVentanaMinSuma()
   - conflictosEnLinkCoreVentana() con el MISMO bug
   - Esto explica su desplome simultáneo tras DirectedWeightedMultigraph

1. Primer intento falla → Rollback simple → Slots zombie

3. Más rollbacks → Más slots zombie
4. Eventualmente: 100% de ventanas contaminadas
5. Resultado: 0% éxito en todos los algoritmos
